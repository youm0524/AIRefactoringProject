실제 API 검증은 `demo2@careerpick.kr` 소유의 기존 초안이 없는 공고 두 개를 골라 실행했다. 타 사용자 확인에는 `demo@careerpick.kr`을 사용했다.

1. 서로 다른 공고에서 초안 신규 생성 `201`.
2. 공고별 답변·공백·줄바꿈·이모지·빈 답변 저장 및 재조회 일치. 기존 공고 재생성 `200`에서 ID·답변·수정 시각 유지.
3. 미인증·유효하지 않은 토큰에서 생성·목록·상세·수정·삭제 모두 `401`.
4. 다른 사용자 목록에서 테스트 초안 제외, 직접 상세·수정·삭제는 모두 `404`. 소유자 답변 불변.
5. 701자 답변 저장은 `400`, 기존 답변·수정 시각 불변.
6. 없는 공고 생성 `404`, 음수 페이지 `400`.
7. 삭제 `204`, 삭제 후 상세·수정·재삭제 `404`, 같은 공고 재작성은 다른 ID·빈 답변의 `201`.
8. 이번 실행에서 생성한 초안만 삭제하고, 두 번째 계정의 기존 목록과 수정 시각이 실행 전과 정확히 일치함을 확인.

DB 테스트에는 개발 DB 대신 별도 `careerpick_step9_test_20261102`, `careerpick_step9_migration_20261102` DB를 생성했다. 다음 재검증에서도 마이그레이션용 DB는 새로운 빈 DB를 사용한다. 실행 방법은 [백엔드 안내](../../backend/BACKEND.md)의 MySQL 테스트 절차를 따른다.

## 4. 완료 범위와 제한

Issue #7의 1~9단계 구현·검증·문서 정리를 완료했다. 전체 lint의 기존 오류는 별도 정리 대상으로 남는다. 자동 저장, 새로고침·브라우저 닫기 경고, 기존 로컬 초안 자동 이전은 범위에 포함하지 않는다. 세션 복구는 메모리를 사용하므로 새로고침하면 미저장 입력이 사라진다. 동시 저장의 충돌 버전 검사는 제공하지 않는다.
