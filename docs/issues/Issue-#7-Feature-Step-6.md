## 1. 목표와 범위

본인 자기소개서의 문항·답변을 불러오고, 답변 전체 저장과 초안 삭제를 제공한다. 기존 인증·DTO·Repository·트랜잭션 처리를 재사용한다. 화면 구현은 7·8단계에서 진행한다.

## 2. 구현할 API

경로의 `coverLetterId`는 공고 ID가 아닌 자기소개서 초안 ID다. 모두 Bearer 인증이 필요하다.

| 기능 | 메서드·경로 | 요청 | 성공 응답 |
| --- | --- | --- | --- |
| 상세 조회 | `GET /api/cover-letters/{coverLetterId}` | 초안 ID | `200` + 기존 상세 DTO |
| 답변 전체 저장 | `PUT /api/cover-letters/{coverLetterId}` | `{items: [{id, answer}, ...]}` | `200` + 갱신된 상세 DTO |
| 삭제 | `DELETE /api/cover-letters/{coverLetterId}` | 본문 없음 | `204`, 응답 본문 없음 |

- 상세는 공고 정보·생성/수정 시각·문항별 질문/답변/글자 제한을 포함하고 문항 순서대로 반환한다. 조회 시 수정 시각을 바꾸지 않는다.
- 저장은 모든 문항의 답변을 받아 한 트랜잭션으로 반영한다. 질문·소유자·공고·글자 제한을 변경하는 기능은 제공하지 않는다.
- 문항 누락·중복·타 초안 문항 ID·NULL·길이 초과는 `400`으로 거절한다. 빈 답변과 공백은 보존하고 UTF-16 기준 700자 제한을 적용한다.
- 저장 성공 시 부모 수정 시각을 갱신한다. 하나라도 검증에 실패하면 답변·수정 시각 모두 유지한다. 동시 저장은 기존 결정대로 마지막 저장을 적용한다.
- 삭제는 초안과 문항·답변을 함께 실제 삭제한다. 사용자·공고는 유지하며, 같은 공고에서 다시 작성하면 새 초안을 생성할 수 있다.

## 3. 추가·수정할 파일

## 4. 작업 순서

- [x] **공통 접근 검사:** 인증 후 `findByIdAndUserId`로 본인 초안을 조회한다. 없는 초안과 타인 초안 모두 `404 COVER_LETTER_NOT_FOUND`로 반환한다.
- [x] **상세 조회:** 읽기 트랜잭션 안에서 기존 상세 DTO로 변환한다.
- [x] **저장 요청 검증:** 목록·각 항목·ID·답변을 검증하고 중복 ID는 Map 변환 전에 거절한다. 잘못된 경로 ID·JSON도 `400`으로 처리한다.
- [x] **답변 저장:** 기존 `CoverLetter.updateAnswers`를 사용하고, 트랜잭션 커밋 성공 후 갱신된 상세를 반환한다.
- [x] **삭제:** 본인 초안을 하나의 쓰기 트랜잭션으로 삭제하고 `204`를 반환한다. 삭제된 초안 재삭제는 `404`로 처리한다.
- [x] **오류 처리:** `{code, message}`를 유지한다. 기존 `404 JOB_NOT_FOUND`를 보존하면서 초안 없음 코드를 분리하고, `401`·`400`·`500`도 검증한다.
- [x] **검증·문서 갱신:** 아래 테스트와 기존 전체 테스트를 실행하고 결과를 기록한다.

## 5. 검증 및 완료 기준

- 생성 → 상세 → 두 문항 수정 → 저장 → 다시 조회한 답변·수정 시각이 일치한다.
- 700자·빈 답변·공백은 저장되고, 초과 길이·NULL·누락·중복·타 초안 문항은 거절된다. 실패 후 재조회 시 기존 값이 유지된다.
- 다른 사용자의 조회·저장·삭제는 모두 `404`, 인증 없음·만료는 `401`이며 데이터가 변경되지 않는다.
- 삭제 후 상세 조회는 `404`, 목록에서는 사라지고 문항도 남지 않는다. 같은 공고로 재생성하면 새 ID와 빈 답변을 받는다.
- Controller·서비스 테스트와 개발 DB에서 분리된 실제 MySQL 통합 검증을 수행한다. 생성·목록·로그인 등 기존 테스트도 통과해야 한다.

## 6. 실행 결과

- 전체 테스트 27개 통과, 실패·건너뜀 없음. 개발 DB와 분리된 MySQL 8.4에서 검증했다.
- 상세 → 저장 → 재조회, 실패 시 답변·수정 시각 유지, 타인 접근 거절, 삭제 후 문항 정리·재생성을 확인했다.
- 동시 저장은 부모 행 잠금으로 순서대로 처리해 서로 다른 요청의 문항 답변이 섞이지 않도록 했으며 통합 테스트로 확인했다.
- 기존 생성·목록·인증·마이그레이션 검증도 통과했다. 화면 구현은 아직 진행하지 않았다.
