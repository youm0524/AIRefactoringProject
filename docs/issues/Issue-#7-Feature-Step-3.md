## 1. 작업 목표

목록·상세·저장·삭제 화면에 필요한 데이터와 서버 계약을 정해 4~6단계 구현의 기준으로 사용한다. 사용자가 작성한 결정 결과와 삭제 추가 합의를 반영한 계약이다.

## 2. 데이터 구조 제안

관계: 사용자·공고 하나의 조합에 초안 1개, 초안 하나에 문항별 질문·답변 여러 개를 연결한다.

| 테이블 | 주요 필드 | 저장할 내용 |
| --- | --- | --- |
| `cover_letters` | `id`, `user_id`, `job_id`, `created_at`, `updated_at` | 초안의 소유자·연결 공고·생성 및 수정 시각 |
| `cover_letter_items` | `id`, `cover_letter_id`, `question_key`, `question_text`, `display_order`, `max_length`, `answer` | 초안별 문항과 답변 |

- `(user_id, job_id)`와 `(cover_letter_id, question_key)`의 중복을 DB에서 금지한다. 공고·사용자 연결은 필수다.
- 최초 생성 시 기존 두 질문을 복사하고 답변은 빈 문자열로 저장한다. 문항 키는 `motivation`, `experience`, 제한은 각각 700자다.
- 질문을 초안에 복사해 보관하면 이후 기업별 문항을 도입해도 기존 질문을 유지할 수 있다. 기업별 원본 문항 관리 기능은 이번 범위에서 제외한다.
- 시각은 Java `Instant`, DB UTC, API ISO 8601로 처리하고, 화면에서 한국 시간으로 표시한다. 생성 시 두 시각을 설정하고 저장 성공 시 `updated_at`을 갱신한다.
- 기업명·공고명은 연결된 공고의 현재 값을 사용한다. 기존 로컬 초안은 읽거나 자동 이전하지 않는다.

## 3. API 계약 제안

모든 자기소개서 API는 Bearer 인증이 필요하다. 사용자 ID는 요청 본문이 아닌 세션에서 확인하고, 본인 데이터만 조회·수정·삭제한다.

| 기능 | 메서드·경로 | 요청 | 성공 응답 |
| --- | --- | --- | --- |
| 공고별 초안 생성 또는 기존 초안 반환 | `POST /api/cover-letters` | `{jobId}` | 신규 `201`, 기존 `200` + 상세 |
| 목록 | `GET /api/cover-letters?page=0&size=20` | 페이지 조건 | `200` + `{items, page, size, totalElements}` |
| 상세 | `GET /api/cover-letters/{coverLetterId}` | 초안 ID | `200` + 상세 |
| 삭제 | `DELETE /api/cover-letters/{coverLetterId}` | 초안 ID, 본문 없음 | `204`, 응답 본문 없음 |
| 답변 저장 | `PUT /api/cover-letters/{coverLetterId}` | `{items: [{id, answer}, ...]}` | `200` + 저장된 상세 |

- 삭제는 초안과 문항·답변을 한 트랜잭션에서 실제 삭제한다. 없는 대상·타인 초안은 `404`로 처리하며, 삭제 후 같은 공고로 새 초안을 생성할 수 있다.
- 공고의 작성 시작 버튼은 POST를 사용하고, 목록의 기존 초안 선택은 상세 GET을 사용한다.
- 목록 항목: `id`, `jobId`, `company`, `jobTitle`, `updatedAt`. 정렬은 `updatedAt DESC, id DESC`로 고정한다.
- 상세: 목록 항목의 필드 + `createdAt` + `items`. 문항은 `displayOrder` 순으로 반환한다.
- 문항 항목: `id`, `questionKey`, `questionText`, `displayOrder`, `maxLength`, `answer`.
- 저장은 모든 문항의 답변을 한 번에 반영한다. 문항 누락·중복·다른 초안의 문항 ID·NULL·길이 초과는 거절하고, 실패 시 전체를 반영하지 않는다. 빈 답변은 허용한다.
- 요청으로 질문·소유자·글자 제한을 바꾸지 못하게 한다. GET에서는 생성하지 않으며, 동시 생성도 DB 유일성 제약으로 초안 1개를 보장한다.
- 오류 형식: `{code, message}`. `400` 입력 오류, `401` 인증 없음·만료, `404` 공고·초안 없음 또는 타인 초안, `500` 서버 오류로 구분한다.

## 4. 결정할 사항

| 항목 | 추천안 | 결정 결과 |
| --- | --- | --- |
| 문항 저장 구조 | 위의 초안·문항 2개 테이블, 생성 당시 질문 복사 | 추천안 적용 |
| 생성·저장 계약 | 위 API 적용, 기존 초안 반환 시 답변·수정 시각 유지 | 추천안 적용 |
| 목록 페이지 처리 | 페이지당 기본 20개, 최대 100개, 이전·다음 이동. 잘못된 조건은 `400` | 추천안 적용 |
| 동시 저장 | 이번에는 마지막으로 저장에 성공한 답변 적용. 충돌 감지·버전 관리는 후속 작업 | 추천안 적용 |
| 글자 수 | 기존 textarea와 같은 UTF-16 길이 기준으로 프론트·서버 모두 700자 검사, 공백 유지 | 추천안 적용 |
| 재로그인 사용자 구분 | `UserView`에 `id` 추가, 로그인·내 정보 응답으로 동일 사용자 확인 | 추천안 적용 |
| 삭제 관계 | 사용자·공고 삭제는 초안이 있으면 제한, 초안 삭제 시 문항 함께 삭제. 본인 초안 삭제 API 제공 | 삭제 포함으로 변경 확정 |
