# 커뮤니티 기능 개선 요구사항

## 문서 상태

- 상태: 승인됨
- 승인일: 2026-10-28
- 유형: 기능 개선 및 오류 수정

## 요구사항 요약

공고별 토글 채팅을 제거하고, 기업별 채팅방을 관리하는 독립 커뮤니티 탭으로 전환한다. 사용자는 공고를 통해 기업 채팅방에 참여하며, 커뮤니티 탭에서 참여 중인 방을 관리하고 실시간으로 대화한다.

## 기능 범위

- 기업당 하나의 채팅방 제공
- 동일 기업의 모든 공고가 같은 채팅방 공유
- 공고의 커뮤니티 버튼을 통한 참여 및 입장
- 참여 중인 기업 채팅방 목록
- 채팅방 선택 및 메시지 송수신
- 최신 메시지 50개 조회
- 채팅방 나가기 및 재참여
- WebSocket 실시간 메시지 송수신
- Redis Pub/Sub을 통한 서버 간 메시지 중계
- 기존 공고별 메시지를 기업 채팅방으로 병합

## 기대 동작

1. 로그인 사용자가 공고의 커뮤니티 버튼을 누르면 해당 기업 채팅방에 참여하고 바로 입장한다.
2. 이미 참여 중이면 중복 참여 없이 바로 입장한다.
3. 비로그인 상태에서 누르면 로그인 창을 표시한다.
4. 로그인 성공 후 원래 선택한 기업 채팅방에 자동 참여하고 입장한다.
5. 비로그인 사용자가 상단 커뮤니티 탭을 누르면 로그인 창을 표시하고, 로그인 후 커뮤니티 탭으로 이동한다.
6. 커뮤니티 탭에는 참여 중인 기업 채팅방만 표시한다.
7. 커뮤니티 탭 진입 시 채팅방을 자동으로 선택하지 않는다.
8. 데스크톱에서는 왼쪽에 목록, 오른쪽에 채팅창을 배치한다. 선택 전에는 채팅방 선택 안내를 표시한다.
9. 모바일에서는 목록을 먼저 표시하고, 선택 시 채팅창으로 전환한다.
10. 채팅방 목록은 마지막 메시지 시각을 기준으로 최근 활동 순으로 정렬한다.
11. 나가기를 누르면 확인창을 한 번 표시한다.
12. 나가기를 확정하면 참여 관계만 제거하고 목록과 실시간 구독에서 제외한다.
13. 사용자가 작성한 메시지와 기존 대화는 삭제하지 않는다.
14. 공고를 통해 다시 참여하면 기존 대화의 최신 50개를 볼 수 있다.

## 예외 동작

- 참여하지 않은 사용자는 채팅방 메시지를 조회·전송·구독할 수 없다.
- 채팅방이 비어 있어도 정상적으로 참여할 수 있다.
- WebSocket 재연결 후 REST API로 최신 50개를 다시 조회해 누락 가능성을 보완한다.
- DB 저장에 실패한 메시지는 Redis 또는 WebSocket으로 전송하지 않는다.
- 백엔드나 Redis 연결 실패 시 성공한 것처럼 표시하지 않고 오류 상태를 안내한다.

## 비범위

- 읽지 않은 메시지 수 및 알림
- 읽음 확인과 입력 중 표시
- 파일 및 이미지 전송
- 채팅방 검색
- 메시지 수정·삭제
- 과거 메시지 추가 불러오기
- 채팅방 생성·관리용 관리자 화면

## 기존 시스템 영향

- 현재 `job_id` 기준 메시지 구조를 기업 채팅방 기준으로 변경해야 한다.
- 사용자와 채팅방의 참여 관계가 새로 필요하다.
- 기존 메시지는 같은 기업명에 속한 공고들을 기준으로 시간순 병합한다.
- 현재 커뮤니티 메뉴의 페이지 하단 스크롤 동작을 독립 페이지 이동으로 변경한다.
- 토글형 `JobChat` UI는 커뮤니티 페이지 구조로 대체한다.
- 기존 로그인과 Redis 세션 구조는 유지한다.

## 완료 및 검증 기준

- 같은 기업의 서로 다른 공고에서 입장해도 동일한 채팅방이 열린다.
- 중복 참여 데이터가 생성되지 않는다.
- 참여·나가기·재참여 흐름이 정상 동작한다.
- 비로그인 및 미참여 사용자의 접근이 차단된다.
- 최신 메시지가 여러 접속자에게 실시간 반영된다.
- 여러 서버 인스턴스에서도 Redis를 통해 메시지가 전달된다.
- 목록이 최근 메시지 순으로 갱신된다.
- 기존 메시지가 기업별로 병합되고 유실되지 않는다.
- 데스크톱과 모바일에서 목록 및 채팅 이동이 정상 동작한다.

## 미결정 사항 및 위험

- 현재 기업 전용 ID가 없으므로 기존 데이터 병합 시 기업명 일치를 사용해야 한다. 상세 설계에서는 안정적인 기업 식별자를 정의해야 한다.
- Redis Pub/Sub은 전달을 영구 보장하지 않으므로 DB 선저장과 재조회 복구가 필요하다.
- 구체적인 WebSocket 프로토콜과 인증 전달 방식은 기술 결정 기록에서 확정한다.
