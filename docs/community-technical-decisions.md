## 현재 제약

- 백엔드는 Java 17, Spring Boot 3.5.7, Spring MVC와 JPA를 사용한다.
- MySQL 8.4와 Flyway가 영속 데이터와 스키마 변경을 관리한다.
- Redis 7과 Spring Data Redis가 이미 로그인 세션에 사용되고 있다.
- 현재 메시지는 `job_id` 기준이며 기업과 채팅방을 나타내는 별도 모델이 없다.
- 프론트엔드는 React 19이며 현재 채팅은 REST 요청으로만 갱신된다.

## 결정

### 1. 기업 채팅방에 안정적인 ID를 부여한다

기업명 문자열을 메시지와 참여 관계의 키로 직접 사용하지 않고 기업별 채팅방 ID를 둔다. 동일 기업의 공고는 같은 채팅방을 참조하고, 사용자와 채팅방의 참여 관계에는 `(user_id, room_id)` 유일 제약을 둔다.

이유:

- 기업명이 바뀌어도 메시지와 참여 관계의 식별자가 유지된다.
- 같은 기업의 여러 공고가 하나의 방을 공유한다는 규칙을 데이터베이스에서 보장할 수 있다.
- 중복 참여와 공고별 채팅방 재생성을 막을 수 있다.

기존 데이터는 `jobs.company`가 정확히 같은 공고를 같은 기업으로 보고 한 채팅방에 병합한다. 별도 기업 엔티티 도입은 이번 기능에 필요하지 않아 제외한다.

### 2. 영속 데이터의 기준은 MySQL로 유지한다

채팅방, 참여 관계와 메시지는 MySQL에 저장한다. Redis는 메시지 원본을 보관하지 않는다.

이유:

- 메시지와 참여 상태는 서버 재시작이나 Redis 장애 후에도 남아야 한다.
- 참여 여부 검증과 나가기 처리를 트랜잭션으로 보호할 수 있다.
- 기존 JPA와 Flyway 운영 방식을 그대로 사용한다.

### 3. 실시간 송수신에는 WebSocket을 사용한다

채팅방을 연 사용자는 WebSocket 연결을 통해 메시지를 송수신한다. 참여·나가기·참여 방 목록과 최초 메시지 50개 조회는 REST API로 처리한다.

이유:

- 새 메시지를 받기 위해 반복 조회할 필요가 없다.
- SSE와 달리 하나의 연결에서 양방향 메시지 처리가 가능하다.
- 채팅방별 구독과 연결 종료 시 구독 해제를 명확하게 관리할 수 있다.

검토한 대안:

- Polling: 구현은 작지만 조회 지연과 반복 요청이 발생해 실시간 채팅 요구에 맞지 않는다.
- SSE: 서버의 실시간 전송에는 충분하지만 클라이언트 전송은 별도 HTTP 요청이 필요하다.

### 4. Redis Pub/Sub을 처음부터 서버 간 중계에 사용한다

메시지는 MySQL 트랜잭션이 성공한 뒤 Redis 채널에 발행한다. 각 서버는 Redis를 구독하고, 자신에게 연결된 해당 채팅방 사용자에게 WebSocket으로 전달한다.

이유:

- Redis 의존성, 실행 환경과 운영 설정이 이미 존재해 추가 인프라 비용이 작다.
- 서버가 여러 대가 되어도 다른 서버에 연결된 사용자에게 같은 메시지를 전달할 수 있다.
- 단일 서버 전용 전송을 나중에 Redis 구조로 교체하는 중복 작업을 피한다.

Redis Pub/Sub은 전달을 보장하지 않는다. 대신 메시지를 MySQL에 먼저 저장하고 WebSocket 재연결 시 최신 메시지를 다시 조회해 누락을 복구한다.

검토한 대안:

- 서버 내부 전송 후 추후 Redis 도입: 초기 코드는 조금 작지만 다중 서버 전환 시 전송 경로와 테스트를 다시 변경해야 한다.
- Redis Streams: 재처리와 소비 이력이 필요한 작업에는 적합하지만, 원본을 MySQL에 저장하고 최신 50개로 복구하는 현재 범위에는 과하다.

### 5. 초기 조회와 복구는 최신 50개로 제한한다

채팅방 입장 또는 WebSocket 재연결 시 REST API로 최신 메시지 50개를 조회하고 화면에는 오래된 순서부터 표시한다.

이유:

- 승인된 범위에서 과거 메시지 페이지네이션이 필요하지 않다.
- 초기 응답 크기와 렌더링 비용을 제한한다.
- Pub/Sub 또는 네트워크 연결 중 놓친 최근 메시지를 간단히 복구한다.

## 메시지 처리 순서

```text
클라이언트 WebSocket 전송
  → 로그인 및 채팅방 참여 검증
  → MySQL 메시지 저장 및 트랜잭션 커밋
  → Redis Pub/Sub 발행
  → 각 서버의 Redis 구독자 수신
  → 해당 서버에 연결된 참여자에게 WebSocket 전달
```

DB 저장이나 커밋이 실패하면 Redis에 발행하지 않는다. Redis 발행이 실패해도 저장된 메시지는 재입장 또는 재연결 시 REST 조회로 확인할 수 있다.

## 보안 기준

- REST 요청과 WebSocket 연결 모두 기존 opaque 로그인 토큰으로 사용자를 확인한다.
- 채팅방 참여자만 메시지를 조회·전송·구독할 수 있다.
- 나가기 완료 즉시 해당 채팅방 구독과 전송 권한을 제거한다.
- 클라이언트가 보낸 작성자명이나 사용자 ID를 신뢰하지 않고 인증된 사용자 정보로 결정한다.

## 구현 전에 확정할 세부 사항

- WebSocket 메시지 프로토콜로 STOMP를 사용할지 단순 JSON 프로토콜을 사용할지
- WebSocket 연결 시 토큰 전달과 만료 처리 방식
- Redis 채널 이름과 중복 전달 방지 방식
- 트랜잭션 커밋 이후 Redis 발행을 보장하는 Spring 이벤트 처리 방식

위 항목은 요구사항을 바꾸지 않는 구현 세부 사항이며, 구현 직전에 가장 작은 안전한 방식으로 확정한다.
